# 高达SEED C.E. 汉化版：USB 模式 OP 开头停住 —— 结论与验证

## 0. 结论（原版完整日志到手后定稿）

**先看数据：两版 OP 的数据量、时长、平均需求几乎完全一样**（都是实测，两份完整日志）：

| 指标 | 原版（完整日志） | 汉化版（完整日志） |
|---|---|---|
| OP 数据 LBA | 574045 .. 621389（探测读 574044） | 574095 .. 621439（探测读 574094） |
| 总读取量 | **47345 扇区 = 92.47 MiB** | **47345 扇区 = 92.47 MiB** |
| 播放窗口（FMV started→ended） | 109.398 s | 110.025 s |
| **平均需求速率** | **886 KB/s = 7.09 Mbps** | **881 KB/s = 7.05 Mbps** |
| 每轮读盘结构 | 3+64+64+61 = 192 扇区 | 1+64+64+63 = 192 扇区 |
| 起播瞬间已缓冲 | 193 扇区 = 0.377 MiB | 193 扇区 = 0.377 MiB |

**所以差别不在"平均码率"，而在"什么时候要数据" —— 需求曲线的形状：**

| 窗口 | 原版 | 汉化版 | 倍数 |
|---|---|---|---|
| 前 3 轮（~0.5 s） | 2.15 MB/s | 2.14 MB/s | 1.00x |
| **前 5 轮（~1 s）** | **0.73 MB/s** | **1.93 MB/s** | **2.65x** |
| 前 10 轮（~3 s） | 0.70 MB/s | 1.27 MB/s | 1.81x |
| 前 20 轮（~7 s） | 0.71 MB/s | 1.06 MB/s | 1.48x |
| 前 40 轮（~17 s） | 0.74 MB/s | 0.96 MB/s | 1.31x |
| 每 10 秒窗口（全程） | 653/691/998/806/922/998/922/960/1037/998 KB/s（起伏大、有低谷） | 913/888/875/880/888/880/886/880/867 KB/s（全程平坦、**没有低谷**） | — |
| 最长"完全不读"空档 | **1.52 s**（另有 1.02 / 0.77 / 0.70 s） | 前 40 轮里最长 0.535 s（没有空档） | — |

**结论**：

> 两版起播时都只有 **0.377 MiB（约 0.4 秒）**的预读数据。
> 汉化版起播后第 1 秒就要 **1.93 MB/s** —— USB 1.1 给不出（实测上限 1.0~1.25 MB/s），
> 存货在 1~2 秒内被吃光；而且它全程平坦（每个 10 秒窗口都是 0.87~0.91 MB/s，**没有低谷**），
> 慢链路再也没机会把缓冲补回来 ⇒ 播放器停住、不再发读请求（所以"读盘完全停止"、而按 Start 能跳过）。
> 原版开头只要 **0.73 MB/s**，之后还有 **1.5 秒完全不读**的空档，慢链路正好在那段时间把缓冲补满；
> 因此它中后段反倒更密（0.92~1.04 MB/s）也能靠缓冲垫过去。

为什么这条解释能覆盖全部现象：

| 现象 | 解释 |
|---|---|
| 原版同一个 U 盘正常 | 开头 1 秒只要 0.73 MB/s，且有整段空档让慢链路补缓冲 |
| 汉化版在 **HDD** 上正常 | 硬盘几十 MB/s，1.93 MB/s 毫无压力 |
| 汉化版在 **PCSX2** 上正常（日志就是它给的） | 模拟器读盘 ~3.9 MB/s |
| 汉化版 USB 上"播 1~2 秒音乐后彻底停住、黑屏" | 0.377 MiB 存货 ÷ 1.93 MB/s ≈ 0.2~0.4 秒，加上后续供数不足 ⇒ 1~2 秒内见底 |
| **官方 OPL、其它改版 OPL、Neutrino 全都一样** | 都受同一个 USB 1.1 物理上限约束，不是某个 loader 的 bug |
| 按 Start 能跳过、之后一切正常 | 停的是这段视频的播放线程（它不再要数据），主机/CDVD 链路没死 |
| 换 U 盘也没变化 | 瓶颈在 PS2 的 USB 主控（12 Mbit/s），不在 U 盘 |

**证据等级**：总量/时长/平均/各窗口需求 = **实测**（两份完整日志）；
"开头尖峰吃光预读缓冲 ⇒ 停住" = **推论**（与全部现象一致，但实机取不到日志，无法直接观测到"播放器放弃"那一刻）；
还有一个**不能排除的第二可能**（汉化版每轮开头那笔 1 扇区读是否在 USB 上偶发坏数据），区分办法见 §0.9 末尾。

## 0.5 用完整 FMV 日志反推码率（推荐）

**可以，而且这是最靠谱的做法。** 原理：游戏是流式播 FMV、缓冲有限，
所以**整段动画的"读盘总量 / 播放时长"就等于它的真实数据率**；日志还能顺带给出
开头有没有高码率尖峰（往往就是 USB 上撑不住的地方）。

需要的日志（两份，原版 + 汉化版）：

1. PCSX2 控制台日志要**带时间戳**（你的日志已经有，形如 `7145.1060 DvdRead 574044 (001)`）；
2. **速度 100%**、不要快进/加速，**关掉 Fast CDVD** 之类影响读盘时序的 hack；
3. 从 OP 开始之前一直录到 **OP 结束、读盘停止**（标题/菜单出来）之后几秒再停；
4. 最好再用秒表告诉我 **OP 大概播放了多少秒**，用来交叉校验。

拿到日志后跑：


会输出（下面是故意构造的"汉化版码率 2.7 倍"样例，验证工具正确）：

判读：

| 结果 | 结论 |
|---|---|
| 稳态 ≈ **600 KB/s vs 1600 KB/s（2.6~2.7x）** | 汉化版那段确实要求更高供数（码率更高 or 时间轴更短）⇒ USB 1.1 撑不住，结论成立 |

**重要修正**：之前只看开头 1.5 秒，算出「1.69 MB/s」，那只是**开头的峰值段**；
整段 OP 的平均只有 **0.85 MB/s**。所以正确的说法是：

* 汉化版 OP 平均要 **0.85 MB/s**，而 PS2 USB 1.1 实测持续读大约 **1.0~1.25 MB/s**（理想）、
  带 FAT 与 OPL 开销通常 **0.9~1.1 MB/s** —— 平均就已经**贴着上限、几乎没有余量**；
* 开头 1.1 秒更是要 **1.6 MB/s**，直接**超过 USB 上限**，预读缓冲当场被吃光；
* 之后再怎么读都补不回缓冲（平均也是贴着上限跑），于是**播一两秒就停住**——完全对上现象。

接下来等**原版完整日志**，用同样口径算一遍（平均速率、开头峰值、总扇区、LBA 范围），

| 原版结果 | 结论 |
|---|---|
| 平均 ≈0.6 MB/s（<5 Mbps） | 原版余量充足、汉化版贴/超上限 ⇒ 结论成立，解法是降码率或用 HDD/SMB |
| 平均也 ≈0.85 MB/s | 那"供给不足"解释不成立，要转查内容/读取模式差异 |

### 两版唯一的扇区级结构差异：每轮第一笔读是 3 扇区 vs 1 扇区

| | 文件起始 LBA | mod 16 | 每轮结构 | 尾轮 |
|---|---|---|---|---|
| 原版 | 574044 | 12 | 3+64+64+61 = 192 | 3+64+46 = 113 |
| 汉化版 | 574094 | 14 | 1+64+64+63 = 192 | 1+64+48 = 113 |

两版都是 246 个完整轮 + 1 个 113 扇区的尾轮，总量都是 47345 扇区；
差别只是"对齐到下一个 16 扇区边界"需要补几扇区（3 vs 1）。

**由此产生了 OPL 里的一条代码路径差异**：汉化版每轮都会出现一次"上一笔读 >1 扇区、
紧接着一笔 1 扇区、LSN 正好接上"的形态（246 笔/OP），原版一次都没有。
我此前在 `cdvdfsv/ncmd.c` 里为这种"1 扇区余数读"加过 `REM1_MIN_US` 补丁（给它补 30ms 间隔）——
**实机验证无效（用户用去掉该补丁的版本照样复现）**，本次已把该实验代码**整体回退**
（它只会给汉化版每轮白加最多 30ms 延迟，纯负面）。

### 还不能排除的第二可能（两种机制的区分）

| | 机制 | 预测 | 怎么验证 |
|---|---|---|---|
| **H1（首选，有量化支撑）** | 开头需求 1.93 MB/s 超过 USB 能力 ⇒ 起播缓冲见底 ⇒ 播放器不再要数据 | 停住的时间点依时序会有些浮动；换更快的载体（SMB / MX4SIO / HDD）就正常 | 汉化版在 SMB 或 MX4SIO 上试一次（顺带也是个能玩的方案） |
| **H2** | 每轮那笔 **1 扇区读**在 USB/BOT 路径上偶发返回错误或零数据，游戏把它当致命 | 每次都在同一处停（重复性很好），与"快慢"无关 | ① 连续试 3~5 次，看停住的时间点是否条条一致；② 把汉化版镜像里那个 AFS 条目的起始位置挪 2 个扇区（读盘结构就变成与原版一致的 3+64+64+61）再上 USB——好了就是 H2，没好就是 H1 |

（H2 的镜像错位实验需要重排 ISO 里该文件的 LBA；这个工具我可以写，纯 Python。）

## 2. 解法（按代价排序）

1. **这个游戏用 HDD / SMB / MX4SIO 玩**（都能给 ≥1.5 MB/s）。USB 1.1 的 12 Mbit/s 是硬件天花板，
   任何 loader（包括 Neutrino）都不可能突破 —— 官方 OPL 也一样卡，就是最好的证明。
2. **把汉化版那段 OP 重做一遍**（换回原版视频流、或重压/重排）。
   注意新口径：**不是看平均码率**（两版平均一样，都是 0.88 MB/s），而是要求
   * 开头 1~2 秒的需求 ≤ 1.0 MB/s（现在 1.93 MB/s）；
   * 全程要留出低谷（现在每个 10 秒窗口都平在 0.87~0.91 MB/s，没有喘息）。
   技术上就是替换 AFS 里那一整条（或整段）+ 修正 AFS 条目表/ISO 布局；需要的话我可以写个替换工具。
3. （实验用）**把汉化版镜像里那个 AFS 条目整体后移 2 个扇区**，让它每轮读盘结构变成
   3+64+64+61（和原版一致），再看 USB 上还停不停 —— 用来判定"1 扇区读"是不是元凶（§0.9 的 H2）。
   镜像重排工具我可以写（纯 Python）。

## 1. 关键推论：这不是“永久卡死”，而是“游戏自己不要数据了”

如果 USB 传输真的永久挂住，那么：`bdm_io_sema` 一直被占 → **之后任何一次读盘（包括按 Start 之后的加载）都会跟着挂住**。
你说按 Start 能正常跳过（游戏继续跑），说明 **USB 链路之后是活的** —— 所以：

> 停住的原因是：**某一笔读返回了错误（或返回了坏数据）→ 视频播放器放弃这段流 → 它不再发读请求**。
> “读盘停住”是结果，不是原因。

这也和 HDD 正常吻合（同一份数据、不同设备驱动，错误不出现）。

## 2. USB 读路径上有三种会“让游戏放弃”的失败签名（都已加了日志）

```
EE → cdvdfsv(8 扇区一段) → cdvdman_read → device-bdm.c → bd_defrag(单碎片快速路径)
   → usbmass_bd: scsi_read → USB BOT(CBW/数据/CSW) → usbd → OHCI
```

| 签名 | 日志（调试构建） | 含义 | 修法方向 |
|---|---|---|---|
| **A. 设备层读错误** | `bdm read failed: lsn=… rv=…`；通常前面还有 `usbmass_bd: ERROR: unable to read sector after N retries (sector=0x…)`（这行是他们 ps2sdk 分支里的 M_PRINTF，**默认就会打**） | SCSI 层重试 32 次/2 秒后放弃 → OPL 返回 `SCECdErREAD` → 游戏收到错误、放弃视频 | 有界重试 / 失败补零返回成功（`make USB_READ_RETRY=N` 就是测这个） |
| **B. 静默零填充** | `bdm read ZERO-FILL: lsn=… 超出碎片表范围` 或 `bdm read ZERO-TAIL: lsn=… 只读到 x/y 块`（**本机新增**） | 读失败但请求超出碎片表范围 → OPL **返回成功、内容是 0**；游戏拿到一堆 0，解码器停住 → 不再读盘 | 说明碎片表范围/文件长度和游戏要读的位置对不上 |
| **C. 真的卡住** | `bdm read HUNG: lsn=… sectors=… (N ms and counting)` 每秒刷（**本机新增**） | `usbmass_bd` 里所有 `WaitSema` **都没有超时**，URB 回调没来就永远等；`bdm_io_sema` 一直占着 | 只能在 ps2sdk（usbmass_bd）里加超时+复位（你们之前试过 5 秒超时，后来回退了） |

**一次运行就能分开**：调试构建跑到停住，看最后十行是上面哪一种；如果三种都没有、只是安静下来，那就是数据层问题（§4）。

## 3. 优先做这两个实验

1. **看最后几行日志**（最重要，直接定案）。
   顺便注意启动时 `usbmass_bd` 打的那行 `%08x%08x %u-byte logical blocks`：确认你的 U 盘报告的是 512 还是 4096 字节逻辑块
   （4096 的话 OPL 会走 `DeviceReadSectorsGeneric_2` 那条带 `mediaLsnCount` 截断 + 零填充的分支，完全是另一条路，需要单独看）。
2. **有界重试能不能救回来**：
   ```bash
   make DEBUG=1 IOPCORE_DEBUG=1 USB_READ_RETRY=8
   ```
   * 能过 OP ⇒ 是签名 A（偶发读错误被游戏当致命），修法就是重试（可再加“连续失败才报错”）；
   * 照样停住、且日志里出现 A 的报错 ⇒ 重试也失败，说明是那块数据/那个位置稳定读不出来（驱动器层面），换盘/重拷镜像一试；
   * 日志干净、只有 ZERO-FILL/ZERO-TAIL ⇒ 签名 B，问题在碎片表范围与游戏读取位置的对应关系上。

## 4. 如果三种签名都没有（数据层）

那么读全部成功、数据也正确，是**游戏自己不再要数据**，需要往“汉化版这段视频的数据/时间戳”方向查：

```bash
python3 pc/ps2_iso_entries.py 汉化版.iso --file MOV.AFS --lba 574094 --compare 原版.iso
```
* 打出该 AFS 条目的**真实时长、平均码率**（扫 MPEG-2 pack 头）、日志 LBA 落在条目内什么位置；
* 两版对比：码率/时长是否一致（你已确认“几乎一样”，这条是量化确认）；
* 用它算出**停住时游戏读到条目的百分之几**（如果每次都停在同一个百分比，说明是那段码流本身的问题；如果百分比每次不同，说明是 I/O 时序）。

## 5. 想请你确认的两点

1. **按 Start 跳过之后，游戏能不能继续正常读盘/加载？**（这一条决定签名 A/B 还是签名 C ——
   如果跳过之后一切正常，就基本排除 C；如果跳过之后的下一次加载也卡，那就是 C，得在 ps2sdk 的 USB 驱动里加超时。）
2. **停住时画面是最后一帧冻住还是黑屏？**（冻住更像 A/B：播放器主动放弃；黑屏更像 C。）
