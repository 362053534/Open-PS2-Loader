# 高达SEED C.E. 汉化版：USB 模式下 OP 开头卡死的原因分析

> 输入：两份 PCSX2（模拟器）日志——原版镜像、汉化版镜像，都取在“进入 OP 动画前后”。
> 现象：同一套 OPL 下，**USB 链路**跑原版进 OP 正常，跑汉化版卡在 OP 开头不动。
> 本文结论只针对 USB；SMB/HDD 情况不同，见 §5.2。

---

## 0. 结论（先看这段）

1. **PS2 的 USB 口是 USB 1.1 full-speed（12 Mbit/s = 1.5 MB/s 理论值），实测顺序读只有 1.0~1.25 MB/s**（理想条件、直接读扇区；带文件系统约 0.9~1.0 MB/s）。这是硬件上限，换 U 盘、换 USB 2.0/3.0 的外壳、换 OPL 版本都不会变。
2. 两份日志证明：**汉化版 OP 需要的数据率是原版的 2.7 倍**。
   | | 每轮读 | 轮周期（中位） | 折算数据率 |
   |---|---|---|---|
   | 原版 | 192 扇区（384 KB） | 0.636 s | **0.62 MB/s（≈4.9 Mbps）** |
   | 汉化版 | 192 扇区（384 KB） | 0.232 s | **1.69 MB/s（≈13.5 Mbps）** |
3. 所以：原版 0.62 MB/s 只用到 USB 上限的 ~55%，跑得动；**汉化版 1.69 MB/s 是 USB 上限的 1.4~1.9 倍，物理上喂不满**。
4. 播放器是“环形缓冲、每轮补 384 KB”：供数低于码率 → 缓冲永远填不满 → 停在等下一块数据，不报错、不花屏、不恢复——**正好是“卡在 OP 开头”的表现**。
5. 为什么汉化组和王盘/模拟器用户都没发现？因为光盘（2x CLV ≈ 2.7 MB/s，PCSX2 的光驱模型更快）能喂饱 1.69 MB/s。**只有 USB 用户会撞上这个上限**。
6. 因此：**这不是 OPL 的逻辑 bug，靠改 OPL 代码解决不了**（除非把数据率降下来）。可行方案只有两个方向：
   * **把这段 OP 的数据率降到 ≤5 Mbps**（换回原版视频，或重压）——见 §5.1；
   * **换载体**：HDD 随便喂；SMB 实测约 2~2.5 MB/s，够；MX4SIO 只有 1.2~1.8 MB/s，属于“可能还是不够”的边缘——见 §5.2。

## 1. 日志证据（PCSX2 两份）

> 证据边界：日志是 PCSX2 的，不是 OPL 的。它能证明**游戏要多少数据、什么节奏要**；OPL/USB 能给多少必须靠 §4 的实测。但“需求 > 供给”这一条，光靠这两份日志 + USB 的硬件上限就已经成立。

### 1.1 播放器代码一致，差别全在数据

两份日志这段路径的 pc 完全相同（`001C51DC / 001C51E0 / 001C51E8 / 001C520C / … / 001C5D7C`，随后 `00108484 … 001083A4`、`001193B4 / 002A7D98 / 002A7DA0 / 00119408 / 002A802C / 002A7FBC / 002A7FC0 / 001194A0 / 00119298 / 001191FC / 00118134 / 0011777C`、`FMV started`、`0011DC74 / 0011DCB4 / 0011DAAC / 0011DBB4 / 00119244`）。
⇒ 汉化补丁没改播放代码。

两版都出现 2 次 `DVCI: File cache was not hit. "MOV.AFS;1"`，读法结构也一样：

```
DVCI 未命中 → 读 1 扇区（探测）
DVCI 未命中 → 读 x 扇区 → 64 → 64 → 余数   （x + 64 + 64 + 余数 = 192 扇区 = 384 KB）
```

### 1.2 镜像被重建过

| | 探测扇区 | 第一轮数据 | 轮内切分 |
|---|---|---|---|
| 原版 | 574044 | 574045 起 | `3 + 64 + 64 + 61` |
| 汉化版 | 574094 | 574095 起 | `1 + 64 + 64 + 63` |

* OP 数据整体**后移 50 扇区 = 100 KB** ⇒ 汉化版镜像被重新打包过（MOV.AFS 之前的内容变了，或 MOV.AFS 里这段之前的内容变了）。
* 轮内切分也变了（`3/61` → `1/63`）⇒ 这段视频的数据本身和原版不一样。

### 1.3 关键：每轮读盘耗时两版一样，**轮与轮之间的等待差 4 倍**

把每轮第一笔读的时刻对齐（t0 = 各自日志的第一笔 DvdRead）：

| | 每轮 4 笔读实际耗时 | 轮周期 | 轮之间的等待 |
|---|---|---|---|
| 原版 | ~101 ms（7145.2505→7145.3516） | 0.636 s | **~535 ms**（首轮 1.97 s） |
| 汉化版 | ~101 ms（15478.9307→15479.0313） | 0.232 s | **~130 ms**（首轮 0.226 s） |

* 同样 192 扇区、同样的 PCSX2 光驱模型，**读盘耗时完全相同（~101 ms ≈ 3.9 MB/s）**——说明“设备能读多快”不是变量；
* 差别全在等待：原版每轮等 0.54 s，汉化版只等 0.13 s ⇒ **每轮要消耗的数据量（码率）才是变量**。

汉化版逐轮（相对 t0）：轮起点 0.149 / 0.476 / 0.700 / 0.935 / 1.168 / 1.568 s，周期 0.327 / 0.224 / **0.235 / 0.233** / 0.400 s。
⇒ 稳态 `393216 B ÷ 0.232 s = 1.69 MB/s`；原版 `393216 B ÷ 0.636 s = 0.62 MB/s`。

### 1.4 需求 vs USB 上限

| | 需要的持续数据率 | vs USB 1.1 实测上限（1.0~1.25 MB/s） |
|---|---|---|
| 原版 OP | 0.62 MB/s | ~50~60%，能跑（和你观察到的“原版正常”一致） |
| 汉化版 OP | 1.69 MB/s | **140%~190%，必然欠数据** |

汉化版开局 1.42 s 内就要了 2.1 MB；USB 同期最多给 ~1.4 MB ⇒ 从一开始就欠账，播放器很快耗完预缓冲停在开头。

## 2. USB 链路的天花板在哪

```
EE 的 N 命令 → cdvdfsv(ncmd.c) → cdvdman_read() → DeviceReadSectorsPtr
   → device-bdm.c: DeviceReadSectors()   ← 这里一次就把整段（如 64 扇区=128KB）交给下层
   → bd_defrag_read_cached_indexed()（ps2sdk libbdm）
   → usbmass_bd.irx（USB 大容量存储，SCSI）
   → usbd.irx → PS2 USB 1.1 控制器（OHCI，full-speed 12 Mbit/s）
```

* **硬上限在最后一段**：12 Mbit/s 理论、实测 1.0~1.25 MB/s（sp193 引 Maximus32 的测试：“For USB, Maximus32 got slightly over 1MB/s”，那还是理想条件、不经文件系统的直接扇区读写）。玩家实测 FAT 上 ~900~1000 KB/s。
* 上面任何一层优化（OPL 的读法、SMB 那套缓存、bd_defrag 的索引）都突破不了 12 Mbit/s。
* 社区共识也是这个：高码率游戏的 FMV 在 USB 上必然卡（Gran Turismo 4、瑞奇与叮当等），官方建议换 HDD/SMB/MX4SIO。**本作汉化版 OP 属于同一类问题，只是更极端（13.5 Mbps）。**
* 另外：USBExtreme（UL 分片）和普通 ISO 走的是同一条路，一样受限；用 USB 2.0/3.0 的硬盘盒也没用——瓶颈在 PS2 的主控。

## 3. 为什么表现是“卡在开头”而不是花屏/跳帧

* 播放器每轮要 384 KB，读满一轮才能继续解码（日志里一轮 = `1+64+64+63`）；
* 供数 < 码率时，环形缓冲只会越来越空；PS2 上的 FMV 播放器没有“丢帧继续”的降级路径，它只会等数据；
* 等不到 → 停住 → 不报错、不结束、不恢复，就是你看到的“卡死在 OP 开头”。

## 4. 怎么验证（两条硬指标）

### 4.1 量出你机器上 USB 的真实吞吐

用调试构建（和平常一样，只是加 `IOPCORE_DEBUG=1`）出包，跑游戏时会多出这一行（每秒一次）：

```
usb rate: xxxx KB/s (xxxx KB in 1000 ms)
```

* 跑**原版 OP**：数字应该在 600~1200 KB/s 之间（说明链路正常，且能喂饱 0.62 MB/s），
* 跑**汉化版 OP**：数字会顶在 **1000~1250 KB/s 附近不动**，同时游戏要的是 1690 KB/s——这一行就直接证明了“撞在 USB 上限上”。
  读数实现：`modules/iopcore/cdvdman/device-bdm.c` 新增 `bdmRateAccount()`（USB/MX4SIO/HDD 都走这条 BDM 路径，发布版零开销）。

### 4.2 量出汉化版 OP 到底“胖”了多少

```bash
python3 pc/ps2_iso_entries.py 汉化版.iso --file MOV.AFS --lba 574094 --compare 原版.iso
```

* 会打出 PVD 卷大小 vs 镜像实际大小、MOV.AFS 的 LBA/大小、AFS 条目表（每条视频的大小 / LBA 区间），并标出 574094 落在哪一条；
* `--compare` 给出每条条目相对原版的大小倍数：**倍数 ≈ 码率倍数**（时长相同的话）。预期 2~3 倍，和 §1.4 的 2.7 倍对上。
* 顺带能查汉化版有没有“PVD 卷大小没更新”这类改版镜像的常见毛病。

### 4.3 交叉验证

把**同一个汉化版 ISO 放内置 HDD**（或网卡硬盘）跑一次 OP：

* 能正常播 ⇒ 结论闭环（超的是 USB 带宽，不是镜像/补丁坏了）；
* 在 HDD 上也卡 ⇒ 那才需要另找原因（AFS 越界、视频截断、卷大小不对等，用 §4.2 的脚本查）。

## 5. 解决

### 5.1 治本（唯一真正有效的方向）：把这段视频的数据率降下来

目标：**≤5 Mbps 总码率（≈0.62 MB/s，和原版一致）**，这样 USB 上还有 ~40% 余量。两条路：

* **换回原版 OP 段**：如果汉化没有改动 OP 内容，直接把原版 MOV.AFS 里这一段（用 §4.2 脚本定位条目/LBA）搬回汉化版即可，大小和码率自然回到 4.9 Mbps。
* **重压**：把该段（PS2 的 FMV 一般是 MPEG-2 PS/PSS 流）用 ffmpeg 压到 ≤4.5 Mbps 视频 + ≤256 kbps 音频，帧率/分辨率/制式和原版对齐（PS2 播放器对 MPEG-2 的画面制式比较挑，建议照抄原版参数，只降码率）。

放回去的注意事项（重要）：

* AFS 条目表（offset/size）和 ISO9660 里 MOV.AFS 的文件大小、以及其后所有文件的偏移都要跟着更新；
* **最省事的做法**：新视频 **不大于** 原条目 size，写在原 offset，尾部补 `0x00`，这样 AFS 表不用动。零填充在 MPEG-2 序列结束码之后一般会被解码器忽略，但**务必实测确认**（放完 OP 不花屏、后续正常）；
* 如果不能补零，就得重打包 AFS + 重建 ISO（注意保持可引导、卷大小字段和实际一致）。

### 5.2 换载体（不动镜像）

| 载体 | 实测带宽 | 对 1.69 MB/s 是否够 |
|---|---|---|
| 内置 HDD / 网卡硬盘（ATA） | 几十 MB/s（ATA-66 级） | 够，推荐 |
| SMB（100 Mbit 网卡） | 社区实测 in-game 约 2~2.5 MB/s（峰值 3 MB/s+） | 够（本机以实测为准） |
| MX4SIO（记忆卡口 SD） | 1.2~1.8 MB/s（机型差异大） | **看运气**，FAT/70k 机型偏快，DECKARD 机型更慢 |
| USB 1.1 | 1.0~1.25 MB/s | **不够**（本文） |
| iLink(SBP2) | 约 2 MB/s 级 | 通常够 |

* 注意：`mode 4（跳过视频）` 对本作**无效**——它是把 `sceCdSearchFile` 命中的 `.PSS` 大小置 0（`searchfile.c`），而本作是从 `MOV.AFS` 里自己取索引、直接按裸扇区读，不经过那条路径。

### 5.3 OPL 侧还能做什么（只能省几个百分点，翻不了倍）

* **USB 路径本身没有多余的读**：`device-bdm.c` 收到 64 扇区就读 64 扇区（一次 128 KB 下发给 BDM），没有扇区缓存、也没有预读白读——所以这个 case 上“改读法”没有油水。
* **`cdvdfsv/ncmd.c` 的“余数 1 扇区补时 30 ms”**：汉化版每轮开头正好是“1 扇区紧接上一轮末尾”的余数读（`1+64+64+63`），会**每轮白加 ~25~30 ms 延迟**；原版每轮开头是 3 扇区，一次都不触发。它对带宽没影响，对“何时卡”有影响，可以先做 A/B（把 `REM1_MIN_US` 临时改 0）看看是“卡死”还是“只是更卡”。别直接删：它是 5dedc9d 为了修别的游戏异常加的。
* **真正的极限在 ps2sdk 的 usbd/usbmass_bd**（传输块大小、URB 数量），即使压榨也就 10% 量级，且不能突破 12 Mbit/s——对 1.69 MB/s 的缺口没有意义。
