# 高达SEED C.E. 汉化版：USB 模式下 OP 开头卡死 —— 重新分析

> 前一版把原因写成“汉化版 OP 码率是原版 2.7 倍”，**那是错的**：
> 两段动画文件码率和大小几乎一样（汉化版只是重新打包过）。
> 本文按这个事实重写，只保留日志里真正测到的东西。

---

## 0. 现在能确定的、和不能确定的

**能确定（两份日志直接测到的）**

| | 每轮读 | 每轮读盘耗时 | 轮周期（稳态） | 折算每秒请求扇区数 |
|---|---|---|---|---|
| 原版 | 192 扇区（384 KB） | ~101 ms | **0.636 s** | **0.62 MB/s** |
| 汉化版 | 192 扇区（384 KB） | ~101 ms | **0.232 s** | **1.69 MB/s** |

* 两版**每轮 4 笔读的实际耗时完全一样（~101 ms）**，也就是说“设备/光驱那边有多快”不是变量。
* 差别全在**轮与轮之间的间隔**：原版 ~535 ms，汉化版 ~130 ms。
* 两版都是同一条顺序扫描（LBA 单调递增，无重复读）：`[头][64][64][尾] = 192`，
  只是**分法不同**：原版 `3+64+64+61`，汉化版 `1+64+64+63`。

**关键推论**

* 既然动画文件本身的码率/大小几乎一样，那么**每轮 384 KB 里装着的动画时长就一样**。
* 原版 0.636 s/轮 ≈ 这段 384 KB 动画的播放时长（也说明原版是**按播放速度取数**，取多少播多少）；
* 汉化版 0.232 s/轮 = **比动画的实际数据率高 2.7 倍地在取数**。
  ⇒ 汉化版上，游戏每秒要的扇区数 **比动画真正需要的多出 ~1.7 倍**。

**所以问题不是“文件更胖”，而是“游戏在汉化版上多读了 2.7 倍的扇区”。**
这就是需要解释的现象；USB 只是让它变成卡死：USB 1.1 实测持续读 1.0~1.25 MB/s，
游戏却在按 1.69 MB/s 的节奏要数据（详见 §2）。

> 提醒两个前提，成立与否会影响结论：
> 1. 两份日志的时间基准要可比（同机同设置、都跑在 100%）；两版读盘耗时都是 101 ms，看起来是成立的。
> 2. 原版“0.636 s/轮 = 动画实时时长”需要文件本身验证 —— 新增的码率扫描就是干这个的（§3.1）。
>    如果原版动画真实码率不是 ~4.9 Mbps，上面的换算要跟着改。

## 1. 两份日志的扇区差异（你指的那点）

| | 原版 | 汉化版 |
|---|---|---|
| OP 起始探测读 | 574044（1 扇区） | 574094（1 扇区）→ **整体后移 50 扇区（100 KB）** |
| 每轮开头 | 3 扇区 | **1 扇区** |
| 每轮结尾 | 61 扇区 | 63 扇区 |
| 64 扇区读的对齐 | LBA ≡ 32 (mod 64)，即 64 KB 边界 | LBA ≡ 16 (mod 64)，即 32 KB 边界 |

* 头部+尾部都是 64 扇区，说明两版的 192 扇区分段结构一致（重新打包保留了分段），只是**起点对齐不一样**。
* 这两个差异在 OPL 代码里只有一个地方会被区别对待 —— 见 §4.1 的 `rem1`。

## 2. 为什么在 USB 上会卡死（而不是别的现象）

* 游戏每秒要 1.69 MB/s（汉化版）/ 0.62 MB/s（原版）；USB 1.1 实测持续读 1.0~1.25 MB/s（理想条件直接读扇区也只有 “slightly over 1MB/s”，带 FAT 约 0.9~1.0 MB/s）。
* ⇒ **原版：需求低于上限，能喂饱；汉化版：需求高于上限，喂不满。**
* 播放器按每轮 384 KB 取数：喂不满 → 缓冲越来越空 → 停在等数据（PS2 上的 FMV 播放器没有丢帧降级），表现就是**卡在 OP 开头、不花屏、不报错、不恢复**。
* 这和第 2.7 倍多读是同一件事的两面：多读的那 1.07 MB/s 是 USB 给不出来的。

（如果那 2.7 倍只是开局预读、缓冲填满后会回落到 0.62 MB/s，那 USB 只是“慢一点”而不是卡死；
日志窗口里它一直保持 1.69 MB/s，所以更像是**预读停不下来**——读到的东西没进缓冲/被判无效，于是继续读。）

## 3. 先做这两个验证（能把上面的推断钉死或推翻）

### 3.1 直接量两段动画的真实码率（新增，不需要 PS2）

```bash
python3 pc/ps2_iso_entries.py 汉化版.iso --file MOV.AFS --lba 574094 --compare 原版.iso
```

新加的 `scan_pss()` 会扫该条 AFS 条目里的 MPEG-2 PS pack 头（`00 00 01 BA` + SCR），给出：

```
条目 0 码率扫描 : 时长 99.90 s，平均码率 5.00 Mbps（按条目总大小折算 5.01 Mbps，共 1000 个 pack）
条目 0 码率对比：
  本镜像  : 时长 xx s，平均码率 x.xx Mbps
  对比镜像: 时长 xx s，平均码率 x.xx Mbps
```

* 如果两段确实都是 ~4.9 Mbps → 你说的“码率大小几乎一样”得到独立确认，那 2.7 倍多读就是**游戏读法**问题（继续 §4）。
* 顺便还能看出：日志里的 LBA 落在该条目的百分之几处、这条目一共多少扇区（用来判断游戏是不是在读这条动画之外的区域）。

### 3.2 量 USB 实际吞吐 vs 游戏请求量（新增，调试构建）

`make IOPCORE_DEBUG=1` 出包，运行时会看到：

```
usb rate: xxxx KB/s (xxxx KB in 1000 ms)      ← 设备实际给了多少（新加，device-bdm.c）
cdvdman_read lsn=574095 sectors=1 ...          ← 游戏要了多少（cdvdman 原有调试打印）
bdm read failed: lsn=... sectors=... rv=...    ← 新增：设备层读失败/短读会打出来
BDM image: N fragments in M contiguous runs, K sectors (first @S)   ← 新增：镜像在 FAT 上的碎片情况
```

三种结果对应三种病因：

| 现象 | 结论 |
|---|---|
| rate 顶在 1.0~1.25 MB/s，且没有 `bdm read failed` | USB 带宽被打满，游戏要得太多 → §4 + §5 |
| 出现 `bdm read failed` / 读失败后卡住 | 是读**错误**（碎片/边界/短读），不是带宽 → 顺着这条 log 查 `bd_defrag`/`usbmass_bd` |
| rate 只有几百 KB/s 且毫无规律 | 链路本身有问题（U 盘/线/供电/驱动），先解决这个 |

## 4. OPL 里“按扇区模式区别对待”的地方（USB 路径）

我把 IOP 读路径从头翻了一遍，USB 上**只有一处**会因为 `1 扇区 vs 3 扇区` 而走不同分支：

### 4.1 `rem1`：余数 1 扇区补时（`modules/iopcore/cdvdfsv/ncmd.c`）

```c
#define REM1_MIN_US 30000u
static int rem1_is_remainder(u32 lsn, u32 sectors)
{
    return (sectors == 1 && rem1_have_prev && rem1_prev_sectors > 1 && lsn == rem1_next_lsn);
}
```

* 汉化版每轮开头正好命中：上一轮最后一笔是 63 扇区、结束 LSN 就是这一笔 1 扇区的起点 ⇒ **每轮触发一次**；
* 原版每轮开头是 3 扇区 ⇒ **一次都不触发**；
* 触发时这笔读在把数据交给 EE 之后被 `DelayThread` 拖到至少 30 ms。

**这就是“扇区模式不一样”在 OPL 里唯一的分叉点**，也是这台机器上唯一能解释“同一份代码，两个镜像表现不同”的现成机制。

建议的 A/B（**先做这个**，成本最低）：

1. 临时把 `REM1_MIN_US` 改成 `0`，重出 USB 包，跑汉化版 OP：
   * 如果卡死消失/明显变化 ⇒ 这条就是病根（它当初是为修别的游戏异常加的，需要改成更精确的条件，而不是删）。
   * 如果完全没变 ⇒ 排除，走 §4.2。
2. 对照组：同样改法跑原版（预期无变化，因为原版不触发）。

> 代码里另一处按读长分支的 `sectors > 16`（`cdvdman.c:322`）是 **SMB 专用**扇区缓存，USB 不走；`searchfile.c`/`streaming.c` 里也没有按扇区数的特殊分支（已 grep 确认）。

### 4.2 碎片/对齐路径（ps2sdk 侧）

USB 的读最终是 `device-bdm.c → bd_defrag_read_cached_indexed() → usbmass_bd.irx`（都在 ps2sdk / 你 fork 的 ps2sdk 里）。
重新打包过的镜像在 U 盘 FAT 上的碎片分布不同，128 KB 的读可能被切成多次设备读；你 fork 刚加的「分页取碎片表 + checkpoint 索引」正好在这条路上。

* 用 §3.2 的 `BDM image: ... fragments ... runs` 就能看出汉化版镜像在盘上有多碎；
* 出现 `bdm read failed` 就是这条路径出问题（短读/边界），要回 ps2sdk 的 `bd_defrag.c` / `usbmass_bd.c` 查；
* 快速反证：把汉化版 ISO 重新**连续**写入 U 盘（新格式化后一次拷入），或换一根盘，如果卡死消失 ⇒ 碎片/布局相关。

### 4.3 PVD 卷大小（`mediaLsnCount`）

OPL 会拿 PVD 的卷大小为辅助边界（`cdvdman.c`/`device-bdm.c`）。重新打包的镜像常见“卷大小字段没更新”。
`--lba` 那行脚本输出里会打「PVD 卷大小 vs 镜像实际扇区数」，先确认它和实际一致、且 OP 的 LBA 在范围内。
