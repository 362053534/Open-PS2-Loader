# 高达SEED C.E. 汉化版：进入 OP 就卡死的原因分析（OPL / SMB）

> 输入：两份 PCSX2（模拟器）日志——原版镜像、汉化版镜像，都取在“进入 OP 动画前后”。
> 现象：同一套 OPL（本仓库分支）下，**原版进 OP 正常，汉化版卡在 OP 开头不动**。

---

## 0. 结论（先看这段）

1. 两份日志里**播放器代码完全一样**（关键 pc 一条条对得上），差别只在**数据**。
2. 汉化版 OP 的数据率是**原版的 ~2.7 倍**（384 KB = 393216 B / 轮）：
   | | 每轮读 | 轮周期（中位） | 折算数据率 |
   |---|---|---|---|
   | 原版 | 192 扇区（384 KB） | 0.636 s | **0.62 MB/s（≈4.9 Mbps）** |
   | 汉化版 | 192 扇区（384 KB） | 0.232 s | **1.69 MB/s（≈13.5 Mbps）** |
3. 播放器是“环形缓冲 + 每轮补 384 KB”的结构：只要**平均供数 < 码率**，预缓冲永远填不满，它就会停在“等下一块数据”上——表现就是**卡在 OP 开头（不是花屏、不是报错，也不会自己恢复）**。
4. 模拟器读盘几乎是本机文件读（日志里 4 笔读只花 93 ms，≈4.2 MB/s，是 PCSX2 拟真节流的上限），所以两版都能播；实机光盘 2x CLV ≈ 2.7 MB/s 也够。**OPL-SMB 是 8 KB 一笔、完全串行的请求-应答，吞吐要靠实测**（按 §3 的往返账，量级在 1.2~1.6 MB/s，而这正好压在汉化版的 1.69 MB/s 下方）：原版 0.62 MB/s 有 2 倍以上余量，汉化版就顶不过去了。
5. 更糟的是，本分支里还有**两个只对汉化版这套读法生效**的额外损耗（见 §4）：
   * `DeviceReadSectorsIsoCached` 的预取会被后面的 64 扇区大读重读一遍 → 每轮白读 ~31 扇区（**+16% 流量**）；
   * `cdvdfsv/ncmd.c` 的“余数 1 扇区补时 30 ms”规则**每轮都被触发** → 每轮白扔 ~25~30 ms（占 232 ms 预算的 **10%+**）。
   两项叠加后，汉化版实际需要 SMB 给出 **≈1.9 MB/s** 才不卡。

所以：**最可能是“汉化版 OP 码率 + 本分支两处额外开销”超过了 SMB 的可持续带宽**（不是 OPL 逻辑算错）。要解决，要么把 OPL 的 SMB 吞吐提上去（§6.2），要么把这段视频的码率降下来（§6.3）；先用 §5 的实测把结论钉死。

## 1. 两份日志的对比（证据）

> 证据边界：日志是 PCSX2 的，不是 OPL 的。它们能证明的是**游戏的读法、读的 LBA、以及播放器的消耗节奏**；OPL 内部怎么服务这些读（SMB 往返、重连、缓存）只能靠源码+实测，不能从这两份日志直接看出来。下面 §1 的结论都是“日志能证明的”，§3/§4 是“OPL 源码推出来的，需要实测钉死”。

### 1.1 播放器代码一致

两份日志在这段路径上的 pc 完全相同（`001C51DC / 001C51E0 / 001C51E8 / 001C520C / … / 001C5D7C`，后面紧跟着 `00108484 … 001083A4`、`001193B4 / 002A7D98 / 002A7DA0 / 00119408 / 002A802C / 002A7FBC / 002A7FC0 / 001194A0 / 00119298 / 001191FC / 00118134 / 0011777C`、`FMV started`、`0011DC74 / 0011DCB4 / 0011DAAC / 0011DBB4 / 00119244`）。
⇒ **汉化补丁没有改这条播放路径的代码，差异全部来自数据（视频/镜像布局）。**

两条日志都出现了 2 次 `DVCI: File cache was not hit. "MOV.AFS;1"`，读法结构相同：

```
DVCI 未命中 → 读 1 扇区（探测）
DVCI 未命中 → 读 x 扇区 → 64 → 64 → 余数   （x + 64 + 64 + 余数 = 192）
```

> 小差异：原版日志里多一条 `vaddr 12000070 Size 64`（VU1 微码写）。PCSX2 只在“首次回填”时打印这类行，多半是日志截取窗口不同，不能算证据；建议在完整日志里搜一下 `12000070` 确认。

### 1.2 镜像被重建过

| | 探测扇区 | 第一轮数据 |
|---|---|---|
| 原版 | 574044 | 574045 起（`3+64+64+61`） |
| 汉化版 | 574094 | 574095 起（`1+64+64+63`） |

* OP 数据整体**后移 50 扇区 = 100 KB**：说明 MOV.AFS 之前有文件变了（汉化常用的字库/补丁文件），或者 MOV.AFS 里第一条视频之前的内容变了。⇒ **汉化版镜像是重新打包过的**，不能按原版的文件布局去假设。
* 轮内切分从 `3/61` 变成 `1/63`：同一段 192 扇区，边界随数据走，说明视频内容/分包也变了。

### 1.3 关键：节奏（数据率）差了 2.7 倍

两版都是「1 笔小读 + 64 + 64 + 余数 = 192 扇区」为一轮；把每轮第一笔读的时刻记下来（t0 = 各自日志的第一笔 DvdRead：原版 7145.1060，汉化版 15478.7813）：

| 轮次（192 扇区 = 384 KB） | 原版轮起点 (t−t0) | 周期 | 汉化版轮起点 (t−t0) | 周期 |
|---|---|---|---|---|
| 1（574045 / 574095） | 0.145 s | 2.069 s | 0.149 s | 0.327 s |
| 2（574237 / 574287） | 2.213 s | 0.636 s | 0.476 s | **0.224 s** |
| 3（574429 / 574479） | 2.849 s | — | 0.700 s | **0.235 s** |
| 4（— / 574671） | — | — | 0.935 s | **0.233 s** |
| 5（— / 574863） | — | — | 1.168 s | 0.400 s |
| 6（— / 575055） | — | — | 1.568 s | — |

* 稳态换算：`393216 B / 0.636 s = 618 KB/s`（原版，≈4.9 Mbps）；`393216 B / 0.232 s = 1.69 MB/s`（汉化版，≈13.5 Mbps）。
* 两版**轮内 4 笔读的相对耗时几乎一样**（原版 +0.0005 / +0.034 / +0.066 s；汉化版 +0.001 / +0.030~0.040 / +0.061~0.066 s），也就是说“读盘只是消耗节奏的从动项” ⇒ **周期差就是码率差**。
* 顺带记一下：原版第一轮等了 2.07 s（开场是低码率/近似静止画面），汉化版第一轮只等 0.33 s，也符合“汉化版码率高得多”。
* 汉化版日志末尾比原版多走了一轮多：原版到 574496（第 3 轮中的第 2 笔）就结束了，汉化版已经读到 575056+64 = 575120。**同一段日志窗口里，汉化版多消耗了约 3 轮的缓冲**。

## 2. 为什么“模拟器能过、OPL 卡住”是符合逻辑的

* 播放器结构：每轮要 **192 扇区 = 384 KB**，读满一轮才能继续解码；每轮的开销里，**读盘时间**和**播放器的消耗时间**串在一起。
* PCSX2：读盘 = 读本机 ISO 文件。日志里一轮 4 笔读只用 93 ms（≈4.2 MB/s），原版/汉化版都能“瞬时”喂满。
* 实机光盘：游戏把速度设成 `2x(CLV)`（日志里 `Speed=2x(CLV)`），≈2.7 MB/s > 1.69 MB/s，也够。
* OPL-SMB：**严格串行的“请求-应答”**（见 §3），一轮要 48 个 SMB 事务；供不上时，播放器等不到数据就停住——**卡在开头而不是花屏**，正是这个特征。

## 3. OPL 侧的读取链路与带宽预算

链路：`EE 的 N 命令 → cdvdfsv(ncmd.c) → cdvdman_read() → DeviceReadSectorsPtr → device-smb.c:DeviceReadSectors → smb.c:smb_ReadFile → ReadAndX`。

在这条链路上有三个“天花板”：

1. **每笔 SMB 读最多 8 KB**
   `modules/iopcore/cdvdman/smb.c`：
   ```c
   #define CLIENT_MAX_BUFFER_SIZE 8192      //协商时告诉服务器的本端上限
   #define CLIENT_MAX_RECV_SIZE   8192      //每笔 ReadAndX 最多要多少
   ```
   注释里写得很清楚：这是**故意压小**的（怕 PS2 清不掉收到的帧，触发服务端拥塞避免）。
   ⇒ 一笔 64 扇区读（128 KB）= **16 个往返**；一轮 192 扇区 = **48 个往返**。

2. **发布版加载的是 `ingame_smstcpip`，配置很紧**
   `Makefile:214` 在非调试构建里设 `SMSTCPIP_INGAME_CFLAGS = INGAME_DRIVER=1`，于是
   `modules/network/SMSTCPIP/include/lwipopts.h`：
   * `TCP_WND 10240`（接收窗口只有 10 KB）
   * `PBUF_POOL_SIZE 8`（8×1540 ≈ **12.3 KB** 总缓冲）
   * `TCP_QUEUE_OOSEQ 0`（**乱序包直接丢**，只能等 RTO 重传）
   一个 8 KB 的 ReadAndX 响应就要占 ~6 个 pbuf ⇒ 缓冲几乎没有余量，实际节奏接近“发一个 8 KB、等一个 8 KB”。
   ⇒ 一轮要在播放器的 233 ms 预算内跑完 48 个往返，单个往返必须 ≤ **4.85 ms**（含 PS2 侧 ps2ip、服务器、TCP 重传余量）。稍微抖一下（丢包重传的 RTO 通常是百毫秒级）就整轮超时。

3. **本分支自己的两处额外损耗**（见 §4）：预取白读 +16% 流量、余数补时 30 ms/轮。
   ⇒ 等效需求：`1.69 MB/s × 1.16 ≈ 1.96 MB/s`，并且每轮只有 `233-30 = 203 ms` 用来搬 384 KB。

对照：原版只需 `0.60 × 1.16 ≈ 0.70 MB/s`，每轮 636 ms 预算，怎么都够。

## 4. 本分支里两个「只咬汉化版」的损耗

### 4.1 预取的白读（+16% SMB 流量）

`modules/iopcore/cdvdman/cdvdman.c` 的 `DeviceReadSectorsIsoCached`：≤16 扇区的读会**预取 32 扇区**填窗口；而 ≥17 扇区原本**直接穿透、不看窗口**。于是：

```
读 1 扇区 @L          → 设备读 32 扇区（L..L+31）
读 64 扇区 @L+1       → 穿透直读，把 L+1..L+31 又读了一遍   ← 白读 31 扇区
读 64 扇区 @L+65      → 直读
读 63 扇区 @L+129     → 直读（一轮 192 扇区）
```

每轮白读 ~31 扇区（原版是 29 扇区），**+16% 的 SMB 流量**——在带宽本来就不够的时候是致命的。
（前提：配置里 `zso_cache` 非 0 —— `initIsoSectorCache()` 用的是这个值，`<32` 会被抬到 32；如果它是 0，SMB 普通 ISO 缓存根本没开，这条损耗也就不存在。）
**已修改**：大读先吃掉窗口能覆盖的开头，剩下的尾巴再直读；窗口内容不动。这样预取真正变成了“预读”，每轮省掉 31 扇区。

### 4.2 “余数 1 扇区补时 30 ms”每轮都触发

`modules/iopcore/cdvdfsv/ncmd.c`（5dedc9d 引入）：

```c
/* 余数 1 扇区：上一笔 EE 读 >1 扇区且 LSN 紧挨着。 */
#define REM1_MIN_US 30000u
static int rem1_is_remainder(u32 lsn, u32 sectors)
{
    return (sectors == 1 && rem1_have_prev && rem1_prev_sectors > 1 && lsn == rem1_next_lsn);
}
```

* **汉化版**每轮的第一笔读正好是这种“1 扇区”（上一轮末尾是 63 扇区，LSN 紧挨）⇒ **每轮被补到 30 ms**，即每轮白扔 30 ms 死时间（233 ms 预算的 13%，等效把需求从 1.69 抬到 ~1.94 MB/s）。
* **原版**每轮开头是 3 扇区，永远不匹配这个规则 ⇒ 一次都不触发。

这条规则当初是为了修“余数 1 扇区导致的游戏异常”，不能随手删；建议先做 A/B 试验（把 `REM1_MIN_US` 临时改成 0），确认它对汉化版 OP 的影响，再决定是否改成更细的条件（例如只在“非连续流”场景补时）。

## 5. 怎么验证（建议按顺序做，1~2 小时能定性）

1. **比对两个镜像**（新脚本 `pc/ps2_iso_entries.py`）：
   ```bash
   python3 pc/ps2_iso_entries.py 汉化版.iso --file MOV.AFS --lba 574094 --compare 原版.iso
   ```
   输出会给出：PVD 卷大小 vs 镜像实际大小、MOV.AFS 的 LBA/大小、AFS 里每条视频的大小（**倍数 ≈ 码率倍数**）、以及 574094 落在哪一条视频里。
   ——如果汉化版那条 OP 的大小是原版的 2~3 倍，§0 的结论就坐实了。
2. **实测 OPL 的 SMB 带宽**：用调试构建（`IOPCORE_DEBUG=1`）跑一次原版 OP，看新加的日志
   `SMB rate: xxxx KB/s (… KB in … ms)`。这是判断“够不够 1.9 MB/s”的唯一硬指标。
3. **换载体对照**：同一个汉化版 ISO，
   * 用内置 HDD（APA）跑一次 → **预测：不卡**（HDD 几 MB/s 随便喂）；
   * 用 USB 跑一次 → **预测：比 SMB 更早卡**（USB 1.1 只有 ~1 MB/s）；
   * 用更快的 SMB 服务器（Linux samba、直连网线、关掉 NAS 上的省电/加密）跑一次。
   能过/卡的程度跟带宽一致 ⇒ 带宽结论成立；完全不一致 ⇒ 看 §6.4。
4. **确认前提**：汉化版在模拟器里 OP 能不能放完？
   * 能放完 ⇒ 就是 I/O 带宽问题（本文结论）；
   * 模拟器里也卡在开头 ⇒ 是镜像/补丁自身坏了（AFS 越界、视频截断、PVD 卷大小没更新等），先用第 1 步的脚本查。

## 6. 解决

### 6.1 已经改好的（无损，先跑起来看效果）

* `modules/iopcore/cdvdman/cdvdman.c`：大读先吃预取窗口 → 每轮省 ~31 扇区（≈16% 流量）。
* `modules/iopcore/cdvdman/device-smb.c`：新增 SMB 吞吐统计（`SMB rate: … KB/s`，发布版是空宏不占开销）。

### 6.2 提高 SMB 持续带宽（治本，需要实机验证）

思路：**减少往返次数**（8 KB → 32 KB）并把接收缓冲放大。已经做成开关，默认关闭：

```bash
make SMB_BIGWND=1        # 出测试包；不加就是原来的行为
```

开关打开后：

* `modules/network/SMSTCPIP/include/lwipopts.h`（`INGAME_DRIVER` 分支）：
  * `TCP_WND 10240 → 32768`
  * `PBUF_POOL_SIZE 8 → 32`（32 KB 窗口按 1540 字节/pbuf 估算约需 22 个 pbuf）
  * 想再稳一点可以顺手把 `TCP_QUEUE_OOSEQ 0 → 1`（乱序不丢，少靠 RTO 重传）——这个没做进开关，需要手改
* `modules/iopcore/cdvdman/smb.c`：
  * `CLIENT_MAX_BUFFER_SIZE 8192 → 32768`（协商时告诉服务器本端上限）
  * `CLIENT_MAX_RECV_SIZE   8192 → 32768`（每笔 ReadAndX 要多少；必须小于 `TCP_WND`）
* 代价/风险：
  * **上游当初选 8 KB 是故意的**（smb.c 里的注释：怕 IOP 清不掉收到的帧 → 在途字节爆炸 → 触发服务端拥塞避免 → 更慢）。所以 32 KB 不一定更快，**必须实测**；不行就退到 16384，甚至只放大 `TCP_WND` 不动读长度。
  * in-game IOP 内存多占 ~35 KB（8→32 个 pbuf）。**必须回归** IOP 内存紧张的游戏（比如你之前在弄的瑞奇与叮当3/分裂细胞那批）；
  * 服务器端行为变化（有的 NAS 对大读更敏感）。
* 预期：单笔读 8 KB → 32 KB，一轮 192 扇区的往返次数从 48 降到 12；如果瓶颈是“往返延迟”，吞吐能翻倍以上。
* 判断标准就用 §5.2 的 `SMB rate` 行：**改之前先记一条基线**（原版 OP 稳态、汉化版 OP 卡死前的几秒），再对比开关打开后同场景的数字。

### 6.2b 进一步（往返次数不够少时再动）

* **单笔 SMB 读拆太碎**：`smb_ReadFile()` 里是 `while (remaining) { chunk = min(remaining, CLIENT_MAX_RECV_SIZE_实际) … }`，一笔读干完才返回；也就是说 **64 扇区 = 往返 ×N，而且完全串行**。想再快就得“边收边发”：一笔读没完就预发下一笔（需要 ps2ip 侧支持多笔在途/or 拆两个 socket），改动量大，先看 §6.2 的实测结果再决定值不值得做；
* **省掉每轮开头的 1 扇区预取**：见 §4.1，已修；
* **`rem1` 补时**：见 §4.2，建议先 A/B。

### 6.3 兜底

* 换内置 HDD，或更快的 SMB 环境；
* 让汉化组把 OP 重新压到 ≤4~6 Mbps（音视频合计 ≤8 Mbps），或者自己用工具替换回去（注意 MOV.AFS 的条目表和 ISO 布局要更新）；
* OPL 的 `mode 4`（跳过视频）对本作**大概率无效**：它的实现是 `searchfile.c` 里把 `sceCdSearchFile` 命中的 `.PSS` 大小置 0，而本作是从 `MOV.AFS` 里自己取索引、直接 raw 读，不经过这条路径。

### 6.4 如果实测带宽远高于 1.9 MB/s 却还是卡

那说明不是带宽，转到这三处（都在 SMB 分支里）查：

* **SMB 保活插队**：`smbReconnectThread` 在空闲 120 s 后发 Echo，会不会正好插进 OP 的读取序列（`SMB_ECHO_IDLE_TICKS` / `smb_Echo`）；
* **pending 读队列**：`cdread_pending / cdread_outstand / sync_flag`（2ef9d32 那套）在“一笔读失败”后，`sceCdSync` 会不会永远等不到完成；
* **PVD 卷大小**：脚本会打印“PVD 卷大小 vs 实际扇区数”，汉化版改版镜像很常见卷大小没更新（`mediaLsnCount` 相关路径都在 `cdvdman.c` / `device-smb.c`）。
* 另：把 OP 读取期间 `cdvdman_read` 的日志打开，确认 `DeviceReadSectorsPtr` 有没有返回过错误（EOM/IPI/TRMOPN）。
